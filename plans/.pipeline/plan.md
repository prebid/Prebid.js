# Plan: Add the Sevio userId submodule (sevioIdSystem)
**Total steps:** 2

## Requirement analysis
- Restatement: Add a Prebid.js userId submodule named `sevioId` (GVL 1393). Its `getId` fetches a Sevio user ID from Sevio's Identity service (`POST https://id.adx.ws/identity/resolve`), identified by a required publisher-supplied client ID (`params.clientId`) and, optionally, an email hash (`params.emailHash`). Prebid's core userId storage keeps the ID in a first-party cookie that is read first, with localStorage as the fallback. When only localStorage still holds the ID, the core reads it from there and the cookie is not restored, because nothing besides Prebid core reads the cookie. No ID reaches bids under COPPA, including one already stored. The ID is exposed as an EID (source `adx.ws`), which `sevioBidAdapter` already forwards, and the PR carries the docs a new ID submodule needs.
- Ambiguities: the design forks were resolved by the user on 2026-09-30. ID source: a Sevio server endpoint. Persistence: Prebid core storage with `cookie&html5`. Missing cookie: originally restored from localStorage when missing; on 2026-10-01 the user confirmed nothing besides Prebid core reads the cookie, so it is no longer restored. EID source: `adx.ws`. Bid adapter: unchanged. Still open, as values only: the defaults under Assumptions, which the user can override without changing the design. The endpoint URL and contract are no longer open: they come from the Identity service doc ("Identity&DMP - Phase 1") the user supplied on 2026-10-02. Resolved by the user on 2026-10-02: the call cadence stays as it is (no call on every page view), the response's `syncs` are ignored, an optional email hash is sent, and the EID source stays `adx.ws`.
- Contradictions: (1) In Prebid, storage type, name and expiry are publisher config (`userSync.userIds[].storage`). A submodule cannot set storage defaults, and modules writing their own storage are being phased out (PR_REVIEW.md:111). So "cookie primary, localStorage fallback" is delivered by documenting `cookie&html5` as required and warning when a publisher configures anything else; it cannot be forced. (2) Core defect: `enforceStorageTypeRule` (modules/userId/index.ts:1299-1317) compares each write's single type with the raw `'cookie&html5'` string. With `userSync.enforceStorageType: true` nothing persists; otherwise every write logs a warning. This is fixed in a separate Core PR (task chip raised), and the module docs state the caveat until it ships. (3) The Identity service doc says the AdServer reads the EID whose source is `sevio.com`; the user stated on 2026-10-02 that `sevio.com` is a placeholder there, so the source stays `adx.ws`. (4) CLAUDE.md discourages `application/json` calls because they add a CORS preflight, but the Identity service answers 415 to any other content type, so the module posts JSON; the backend accepting `text/plain` would remove the preflight.
- Assumptions: GVL 1393 is the same legal entity as sevioBidAdapter. The endpoint follows the Identity service's resolve contract (see Decisions). The module takes a required `params.clientId` and an optional `params.emailHash`. No ID is provided under COPPA, including an ID already stored (stricter than SharedID, whose stored ID still reaches bids). The docs recommend storage name `_sevioId` and `expires: 30` days. The maintainer is technical@sevio.com.
- Out of scope: the Core enforceStorageType fix (separate PR); any sevioBidAdapter change, including its string GVLID (modules/sevioBidAdapter.js:17); the untracked modules/sevioAnalyticsAdapter.js; metadata/modules/sevioIdSystem.json (generated by the release process, never hand-edited); root-domain cookie scoping. Acting on the resolve response's `changed` flag (user, 2026-10-02); firing its `syncs` was moved into scope on 2026-10-15. Outside this repo: the Sevio Identity service itself, the prebid.github.io docs PR, and adding the new storage keys to https://sevio.com/tcf.json.
- Pushback / better options considered: a browser-generated UUID would duplicate SharedID (pubcid), which the adapter already receives, so the user chose a server-issued ID. Module-managed cookie and localStorage writes were rejected (review policy; blocked by enforceStorageType and storageControl). Rewriting both stores on every page view (SharedID `extend`) was rejected because it resets `_last` on each visit and so disables `refreshInSeconds`. Restoring a missing cookie through `extendId` was then dropped too (2026-10-01). Nothing outside Prebid reads the cookie, and the core already falls back to localStorage. The module's own cookie read was checked by storageControl while the core's is not (`advertiseKeys: false`, modules/userId/index.ts:1178-1184). It also ignored whether cookies are enabled. In both cases it rewrote both stores and reset `_last` on every page view. Calling the Identity service on every page view through `extendId`, as the service doc's SDK does (which keeps Safari's 7-day cookie clock running and refreshes the recall hint on every visit), was offered on 2026-10-02 and declined by the user in favour of the existing cadence plus a recommended `storage.refreshInSeconds: 86400`.
- Non-functional targets: ID endpoint requests on a page view that already has a valid stored ID (cookie or localStorage): 0. Synchronous network requests made by getId: 0 (the fetch runs only inside the callback Prebid schedules).

## Solution strategy
Per sub-outcome:
- Persist the ID, cookie first, localStorage fallback: existing capability = core userId storage. `getConfiguredStorageTypes` parses the type (modules/userId/index.ts:1037-1039), `setStoredValue` writes every enabled type (189-209), and `getStoredValue` reads in configured order (270-296); strategy = reuse; layer = publisher config documented in the module docs, plus a config check in getId; justification = the core already has exactly this read/write order, while module-managed storage is being phased out and is blocked by enforceStorageType and storageControl.
- Use the ID when the cookie is missing: existing capability = `getStoredValue` falls back to localStorage when the cookie is empty (index.ts:270-296); strategy = reuse; layer = core only (the module has no `extendId` and no StorageManager); justification = nothing besides the core reads the cookie, so restoring it changes no output. A module-side cookie read is exposed to storageControl and to disabled cookies, and either one turns the restore into a rewrite on every page view.
- Suppress the ID under COPPA, including a stored one: existing capability = `coppaDataHandler.getCoppa()` (src/consentHandler.ts:223-240); strategy = reuse; layer = submodule `decode`, plus the existing `getId` guard; justification = the core decodes the stored ID whatever `getId` returns (modules/userId/index.ts:944-947), so only `decode` can keep a stored ID out of bids.
- Fetch the ID from Sevio: existing capability = the server-fetch pattern in modules/startioIdSystem.js and `qualifiedAjaxBuilder` (src/ajax.ts:295-305); strategy = compose; layer = the callback returned by `getId`; justification = plain `ajax` silently drops `withCredentials` for a module that has no metadata yet (src/ajax.ts:149-158, plugins/callerContext.js:12-37). The resolve body's `privacy` object is built in the module rather than with `getUserSyncParams`, which URL-encodes `us_privacy` and joins `gpp_sid` into a string, while the JSON body needs the raw string and an array of numbers.
- Expose the ID as an EID: existing capability = the submodule `eids` property in function form, which allows a numeric atype (modules/sharedIdSystem.ts:196-206; the object form types atype as a string, modules/userId/spec.ts:123). The core consumes it and sevioBidAdapter already forwards it (modules/sevioBidAdapter.js:335-339); strategy = reuse; layer = submodule; justification = no new surface.
- Public types: existing capability = the `declare module './userId/spec'` augmentation of `UserId`, `ProvidersToId` and `ProviderParams` (modules/sharedIdSystem.ts:46-60); strategy = reuse; layer = submodule file; justification = CLAUDE.md and PR_REVIEW.md:22 ask for typed, exported params. `SevioIdParams` is `{clientId: string; emailHash?: string}`.
- Registration and docs: existing capability = the `userId` list in modules/.submodules.json and the doc format of recent ID modules (modules/rediadsIdSystem.md, modules/anonymisedIdSystem.md); strategy = extend; layer = repo docs and config; justification = required by PR_REVIEW.md:104-119.

## Context

Sevio already has a Prebid bid adapter (modules/sevioBidAdapter.js, GVL 1393) that forwards `userIdAsEids` and `userId` to `https://req.adx.ws/prebid`. Sevio now wants its own user ID in Prebid, stored first-party in a cookie (primary) with localStorage as the fallback. Prebid's userId core already supports exactly that through `storage.type: 'cookie&html5'`. The new module therefore concentrates on fetching the ID, keeping it out of bids under COPPA, exposing the EID, types, tests and docs. It never touches storage itself.

The Sevio ID endpoint does not exist yet. Step 1 codes against a single constant and the contract proposed below, and the end-to-end verification refuses to pass while the placeholder is still in place.

**Amended (2026-10-02):** The endpoint now exists: Sevio's Identity service, `POST https://id.sevio.com/identity/resolve`, specified in the "Identity&DMP - Phase 1" doc the user supplied on 2026-10-02. `ID_ENDPOINT` points at it, so the end-to-end placeholder gate passes and stays as a regression guard.

**Amended (2026-10-06):** the final Identity service host is `id.adx.ws` (user, 2026-10-06), so `ID_ENDPOINT` is now `https://id.adx.ws/identity/resolve`; the path and the request contract are unchanged.

- **[user]** The ID comes from a Sevio server endpoint, not from the browser. *Rationale: a browser UUID would duplicate SharedID and draw review pushback.*
- **[user]** Persistence is Prebid core storage with `storage.type: 'cookie&html5'`; the module never writes storage. *Rationale: the core already reads the cookie first and falls back to localStorage; module-managed writes are being phased out.*
- **[user]** No cookie restore. The module has no `extendId` and no StorageManager. When the cookie is missing, the core reads the ID from localStorage, and the cookie stays missing until the next `getId` (refresh, expiry or a consent change) rewrites both stores. *Rationale (amended 2026-10-01; this replaces the original decision, under which `extendId` returned `{id: storedId}` when the cookie was missing): the user confirmed nothing besides Prebid core reads the cookie. The restore's module-side read was checked by storageControl (strict by default) while the core's is not, and it ignored whether cookies are enabled. Either one made it rewrite both stores and reset `_last` on every page view.*
- **[user]** EID source is `adx.ws`, with atype 1. *Rationale: reviewers require the provider's real domain; adx.ws is the domain Sevio's ad serving runs on (req.adx.ws), and atype 1 marks a device-based ID. Amended (2026-10-02): Reaffirmed by the user on 2026-10-02: the Identity service doc's `sevio.com` source is a placeholder.*
- **[user]** sevioBidAdapter is not changed. *Rationale: it already forwards `userIdAsEids` and `userId`.*
- **[user]** `ID_ENDPOINT = 'https://id.adx.ws/identity/resolve'`, the real Identity service endpoint. *Rationale: Amended (2026-10-02): this replaces the placeholder decision (`https://sevio-id-endpoint.invalid/id`), now that the user has supplied the Identity service doc. Amended (2026-10-06): the host changed from `id.sevio.com` to `id.adx.ws`, the final Identity service host chosen by the user.*
- **[user]** The endpoint contract is the Identity service's public resolve: `POST` with `Content-Type: application/json`, sent with credentials. The body is `{client_id, ids?, privacy}`: `ids` holds `sevio:<stored envelope>` and `email_sha256:<hash>` when present, and `privacy` holds `gdpr` (0/1; 0 when Prebid has no boolean `gdprApplies`, amended 2026-10-15), `gdpr_consent`, `us_privacy`, `gpp` and `gpp_sid` (an array of positive section ids; the GPP CMP's -1 is left out). The answer is `{sevio_id, changed, syncs?}`; `sevio_id` is used, and `syncs` are fired (amended 2026-10-15). *Rationale: Amended (2026-10-02): this replaces the planner's proposed GET contract with the contract in the Identity service doc. The service answers 415 to a content type other than `application/json`, so the text/plain preflight saving of the GET proposal is not available.*
- **[planner]** TypeScript module with inline types; `name` and decode key `sevioId`; numeric `gvlid: 1393`. *Rationale: PR_REVIEW.md:22 and :98-100; TCF vendor checks need the GVL ID registered under the module name.*
- **[planner]** `getId` requires `storage`: without it the module logs an error and returns nothing. A `storage.type` other than `cookie&html5` logs a warning but still works. *Rationale: without storage the endpoint would be hit on every page view and nothing would persist; the storage choice stays with the publisher.*
- **[planner]** No ID under COPPA. `getId` makes no request when `consentData.coppa` is set, and `decode` returns `undefined` when `coppaDataHandler.getCoppa()` is true, so an ID already stored never reaches bids. Other consent signals are forwarded to the endpoint. *Rationale (amended 2026-10-01): the core decodes the stored ID whatever `getId` returns (modules/userId/index.ts:944-947), so a getId-only guard, as in SharedID, still leaks a stored ID. GDPR is already enforced by Prebid's TCF checks for GVL 1393, and the remaining signals are the server's to act on.*
- **[planner]** No `domainOverride`, so the cookie is host-only, like localStorage. *Rationale: not requested. `findRootDomain` returns an invalid cookie domain on hosts with a port (e.g. localhost dev pages), and `domainOverrideToRootDomain` adds a probe cookie that would need disclosing. Easy to add later if Sevio wants the ID shared across subdomains.*
- **[planner]** The docs recommend `storage.name: '_sevioId'` and `expires: 30`; maintainer is technical@sevio.com. *Rationale: one fixed recommended name lets https://sevio.com/tcf.json disclose the exact keys; 30 days is a conservative default the user can change; the maintainer matches modules/sevioBidAdapter.md.*

- **[user]** `params.clientId` is required: when it is missing, blank or not a string, `getId` logs an error and returns nothing, so no request is made. *Rationale: Amended (2026-10-02): The Identity service answers 400 without a non-blank `client_id`; the user's wrapper supplies its own value.*
- **[user]** `params.emailHash` is optional. It is trimmed and lowercased, then sent as `email_sha256:<64 hex>` after the stored envelope. Any other shape logs a warning and is not sent. The module never stores it. *Rationale: Amended (2026-10-02): Requested by the user on 2026-10-02. One malformed entry in `ids` gets the whole request refused with 400, so an invalid hash is dropped rather than sent.*
- **[user]** The call cadence is unchanged: no `extendId`, and a request is made only when nothing is stored, when consent changes, or when `storage.refreshInSeconds` elapses. The docs recommend `refreshInSeconds: 86400`. *Rationale: Amended (2026-10-02): Chosen by the user on 2026-10-02 over calling on every page view. A refresh presents the stored envelope and stores the resealed answer.*
- **[user]** The resolve response's `syncs` are fired; `changed` is ignored. A sync fires only when the response carries a non-empty string `sevio_id`, and only for an entry whose `url` is an `https` string (any other entry is skipped with `logWarn`). Each URL must pass `isActivityAllowed(ACTIVITY_SYNC_USER, activityParams(MODULE_TYPE_UID, 'sevioId', {syncType: 'image', syncUrl: url}))`, so TCF Purpose 1 and vendor 1393, `userSync.syncEnabled` and activity controls (including US-state rules) apply; `userSync.filterSettings` does not, because it only covers bidders. It is fired with `politeTriggerPixel`. The module keeps no storage for this: syncs fire only when it calls the service (nothing stored, `refreshInSeconds` elapsed, consent change), and each entry's `ttl` is ignored. *Rationale: Amended (2026-10-15): this replaces the 2026-10-02 decision to ignore `syncs` and `changed`. The user chose firing in the ID module over routing the syncs through `sevioBidAdapter.getUserSyncs`, after being told reviewers may push back because it bypasses `filterSettings` and fires a partner's pixels. The docs say how to block them.*
- **[planner]** The stored ID is presented as `sevio:<id>` only when it is 66 base64url characters. A `null` `sevio_id` logs info and yields no ID; any other malformed answer logs an error. *Rationale: Amended (2026-10-02): A malformed `ids` entry gets the whole request refused with 400. A `null` answer is the service's normal refusal (privacy or agent gate), not a fault.*
- **[planner]** `coppa` is not sent in `privacy`. *Rationale: Amended (2026-10-02): Under COPPA `getId` makes no request at all, so a request that is sent could only ever carry `coppa: 0`, and Prebid's ORTB convention omits the flag when it does not apply.*
- **[user]** `privacy.gdpr` defaults to `0` when Prebid has no boolean `gdprApplies` (no TCF consent management configured); a boolean `gdprApplies` is still sent as 0 or 1. *Rationale: Amended (2026-10-15): chosen by the user on 2026-10-15 after being told that it asserts GDPR does not apply when nothing determined the scope, and that it disables the Identity service's no-consent-signal refusal for `gdpr`. The docs tell publishers with EU traffic to include `consentManagementTcf`.*

    - Only localStorage holds the ID: it is used, no endpoint request is made, and no `_sevioId` cookie is written.
    - Nothing is stored: one request is made, with no `ids`, and responding with `{"sevio_id": <envelope>}` writes `_sevioId` to both the cookie and localStorage.
    - A stored envelope whose `_sevioId_last` is older than `refreshInSeconds: 86400`: one request presents `sevio:<stored>`, and the resealed answer replaces the ID in both stores.
    - A valid stored ID with COPPA on (`config.setConfig({coppa: true})`, then seed `_sevioId_cst` with `getConsentHash()`): `getUserIds()` has no `sevioId`, no `adx.ws` EID is produced, and no endpoint request is made.

**Notes:**
- In the through-core tests, seed `_sevioId_cst` with `getConsentHash()` (and a future `_sevioId_exp` for localStorage). Otherwise the core sees a consent change and calls getId instead of only decoding the stored ID.
- Between tests, reset consent state and call `config.resetConfig()` (which also clears `coppa`), then expire or remove every `_sevioId*` key (`COOKIE_SUFFIXES` / `HTML5_SUFFIXES`).
- The module never reads or writes storage. storageControl and cookie availability only affect the core's own reads and writes, and its manager uses `advertiseKeys: false` (modules/userId/index.ts:1178-1184).
- Known trade-off: once the cookie is lost (e.g. Safari's 7-day cap on cookies set by script), the ID lives only in localStorage until the next `getId` rewrites both stores.
